# Архитектура хранения CDR-данных по звонкам в 3 ЦОД

## 1. Исходные требования

- География: **3 ЦОД** (DC1, DC2, DC3).
- Храним **только CDR/метаданные** (записи разговоров не храним).
- Ограничение на ВМ: **до 3 ТБ дисков**.
- Поступление данных: **500 ГБ за 3 месяца** (только CDR).
- Срок хранения: **3 года**.

## 2. Расчёт объёма хранения (CDR)

1. Скорость роста:
   - 500 ГБ / 3 месяца = **~166.7 ГБ/месяц**.

2. За 3 года (36 месяцев):
   - 166.7 × 36 = **~6 ТБ** полезных CDR-данных.

3. Запас на индексы, VACUUM/compaction, служебные таблицы и переразмещение партиций:
   - коэффициент 1.3.
   - 6 ТБ × 1.3 = **~7.8 ТБ на один ЦОД**.

4. С учётом 3 ЦОД (полная копия в каждом):
   - 7.8 × 3 = **~23.4 ТБ** суммарно по площадкам.

> Ключевое изменение: в объёме больше **нет аудиообъектов**, только табличные CDR-данные и индексы.

## 3. Целевая логическая архитектура (только CDR)

### 3.1 Модель хранения

- Основное хранилище: **распределённая СУБД для CDR** (рекомендация: ClickHouse как основной слой аналитики/ретенции).
- Оперативные транзакционные операции/интеграции: PostgreSQL (опционально) как справочники/служебный OLTP.
- CDR хранится в партиционированных таблицах:
  - partition by month (или week при высокой нагрузке),
  - сортировка по `event_time`, `customer_id`, `call_id`.

### 3.2 Retention и жизненный цикл

- 0–12 месяцев: «горячие» партиции на более быстрых дисках.
- 12–36 месяцев: «тёплые» партиции на более дешёвом классе дисков.
- По истечении 36 месяцев: автоматическое удаление партиций по TTL.

## 4. Физическая схема по 3 ЦОД

### 4.1 Роли ЦОД

- **DC1 (Primary ingest/query)**: приём CDR из биллинга/SBC/телефонии, основной read/write.
- **DC2 (Secondary)**: синхронная/квази-синхронная реплика, приоритетный failover.
- **DC3 (DR)**: асинхронная реплика и контур аварийного восстановления.

### 4.2 Как уложиться в лимит 3 ТБ на ВМ

Проектный объём на ЦОД: ~7.8 ТБ, значит одна ВМ не подходит.

Минимальная практичная конфигурация на ЦОД:
- **3 data-ВМ × 3 ТБ = 9 ТБ** под CDR-данные.
- **3 служебные ВМ** (координаторы/keeper/мониторинг/балансировка) меньшего объёма.

Итого по 3 ЦОД:
- 9 data-ВМ (по 3 на каждый ЦОД) + служебный контур.

## 5. Технологический стек (вариант)

1. **CDR-хранилище**:
   - ClickHouse cluster (ReplicatedMergeTree, партиционирование по времени).

2. **Ingestion**:
   - Kafka/RabbitMQ как буфер перед записью в CDR БД.

3. **Сервис запросов/API**:
   - отдельный stateless-сервис для поисковых запросов и выгрузок.

4. **Резервное копирование**:
   - ежедневные backup-снапшоты CDR-таблиц,
   - ежеквартальные тесты восстановления,
   - контроль целостности партиций.

## 6. SLA и отказоустойчивость

- RPO:
  - DC1→DC2: **0–5 минут**,
  - DC1→DC3: **15–60 минут**.
- RTO:
  - переключение на DC2: **15–30 минут**,
  - восстановление из DC3: **1–4 часа**.

## 7. Безопасность для CDR

- Шифрование at-rest и in-transit (TLS).
- Маскирование персональных данных (номер абонента, идентификаторы) в витринах доступа.
- RBAC по ролям (оператор/аудит/админ).
- Полный аудит операций чтения и выгрузки CDR.

## 8. Итог

- При хранении **только CDR** расчётный полезный объём за 3 года: **~6 ТБ**.
- С учётом служебного запаса: **~7.8 ТБ на ЦОД**.
- Лимит 3 ТБ/ВМ закрывается горизонтальным кластером: **минимум 3 data-ВМ на ЦОД**.
- Архитектура: **Primary + Secondary + DR** с репликацией и проверяемым DR-планом.
